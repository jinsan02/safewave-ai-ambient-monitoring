## 1. 유의사항 — 먼저 읽을 것

- **이 ONNX에는 학습된 가중치가 없다.** DFT 기저를 상수로 넣은 신호처리 그래프다.
  initializer는 추세제거 행렬 2개와 DFT cos/sin 기저 2개, 채널 마스크 1개가 전부다.

- **현재 수집 데이터에서 호흡·심박 신호는 검출되지 않았고 대조군이 역전돼 있다.**
  빈 방 69.1 % 통과 > 활동 56.2 % (호흡), 심박은 95.7 % > 89.6 %.

- **따라서 출력 bpm은 신뢰하면 안 되며 통합 테스트·배선 확인 용도로만 쓴다.**
  런타임이 반환하는 dict에 `trustworthy: False` 가 하드코딩돼 있다. 이 값을 무시하고
  bpm을 생체신호로 쓰는 코드를 만들지 말 것.

- **근거:**
  - raw lag-1 자기상관 **+0.05 ~ +0.11** (0.25 Hz 호흡이면 ~0.9999 가 나와야 함)
  - 전력의 **79 %가 10~50 Hz**, bin당 평균 ~1.0 (백색)
  - ESP 필터 출력 heart/resp 표준편차 비 **1.92 ~ 2.10** = 백색 입력 예측치 √(2.2/0.5)=2.10 과 일치

- **정규화는 원인이 아니다.** 피크 정규화는 양수 스칼라 나눗셈이라 argmax를 바꿀 수 없는데,
  실제로는 **75 % 프레임에서 argmax가 바뀐다.** 즉 잡음은 정규화 이전에 이미 들어와 있었다.

- **게이트 자체는 유효하다.** 백색잡음을 넣으면 통과율 **0 %** 다 (창 30초, 두 대역 모두).
  게이트가 헐거워서 생긴 문제가 아니다.

- **한계:** 정적 자세 전용 녹화가 없어 positive 클래스로 `normal_active` 를 대용했다.

- **다음 진단:** 정규화를 끈 raw를 1분 저장해 lag-1 자기상관 재측정. → 1-1절에서 구체화했다.

## 1-1. 진폭 정보 소실 — 확정된 사실과 아직 갈리지 않은 가설

바로 위의 "정규화는 원인이 아니다"와 **모순되지 않는다.** 서로 다른 이야기다.
정규화는 *지금 보이는 프레임 간 잡음*을 만들지 않았지만, *호흡 성분을 제거하는 별도의 경로*일 수 있다.

### (a) 증명된 사실 — 수학적으로 확실하고 실측으로도 확인됨

프레임 피크 정규화 `x / max(x)` 는 **공통 배율 `a(t)` 에 불변**이다.
`(a(t)·x) / max(a(t)·x) = x / max(x)` 이므로, 모든 서브캐리어에 똑같이 실린
**공통모드 진폭 변조는 정확히 0 이 된다.** 근사가 아니라 항등식이다.

- 검증 [3b]: 0.25 Hz 공통모드 사인파를 넣고 정규화하면 채널별 시간축 표준편차가
  **0.000e+00** — 신호가 완전히 사라진다.
- 검증 [3c]: **차동 변조는 통과한다.** 채널마다 다르게 실린 0.30 Hz 변조는
  `[18. 18. 18.]`, 오차 0.0 으로 정확히 검출된다.

### (b) 별도 실측 — M1 쪽 확인 결과 (이 레포에서 재측정하지 않음)

수집 CSV 의 `raw_*` 는 **34세션 17,034프레임 전부 프레임 피크가 정확히 1.000000** 이다.
즉 **프레임 진폭 정보가 센서 단에서 이미 소실돼 있다.** 정규화를 후처리에서 끄는 것만으로는
되돌릴 수 없다는 뜻이다.

> 출처는 M1 측 확인이고 이 레포에서 그 수치를 재현하지는 않았다.
> 다만 이 레포에서 따로 본 파일의 `raw` 행 최댓값도 전 분위에서 1.0000 이었으므로 어긋나지 않는다.

### (c) 가설 — **아직 검증되지 않았다**

호흡은 진폭 변조이므로, **그 성분이 공통모드로 실린다면** 현재 전처리가 이를 제거하고 있을 수 있다.

다만 이 가설은 **아직 갈리지 않았다.** 호흡이 차동으로 실렸다면 (c)와 무관하게 살아남았어야 하고,
실제로는 차동 성분에서도 아무것도 나오지 않았다. 따라서 지금 데이터만으로는

- "호흡이 공통모드라서 정규화가 지웠다" 와
- "애초에 CSI에 호흡이 실리지 않았다 (수집/AGC/위상 미보정)"

둘 중 어느 쪽인지 **판별할 수 없다.** 단정하지 말 것.

### (d) M1 과의 연결 — 가능성

이 가설이 맞다면 **M1 의 빈 방 오탐과 같은 원인**일 가능성이 있다 (진폭 정보 소실).
두 모듈이 같은 수집 경로를 공유하므로, 원인이 하나면 고치는 것도 한 번이다.
**확인된 인과가 아니라 가능성이다.**

### (e) 갈라내는 방법

펌웨어에서 **정규화 전 프레임 피크값을 프레임당 float 하나로 함께 전송**하고
CSV 에 컬럼을 추가한다. 그 뒤 1분 수집해 lag-1 자기상관을 재측정한다.

- 피크값 계열의 lag-1 이 ~0.99 로 나오면 → 호흡은 공통모드에 있었고 정규화가 지운 것이다
- 여전히 ~0.05 면 → 진폭 정보 자체에 호흡이 없다. 수집/AGC/위상 보정 쪽 문제다

프레임당 float 하나이므로 대역폭 비용이 사실상 없다 (기존 64채널 대비 +1.6 %).

### (f) 우선순위

**10월 1순위를 이 진단으로 올린다.** 근거:

- 비용이 가장 싸다 (펌웨어 한 줄 + 컬럼 하나 + 1분 수집)
- 한 번에 두 갈래를 가른다 (1-1(c))
- M1 과 M2 가 같이 걸려 있을 수 있다 (1-1(d))
- 이게 갈리기 전에는 기준 장비 구매도, 정적 전용 녹화도 의미가 없다 —
  신호가 실려 있지 않으면 라벨이 있어도 배울 게 없다

## 3. 입출력 계약

### 입력

| 이름 | shape | dtype | 비고 |
|---|---|---|---|
| `csi_window` | `(1, 3, 64, 3000)` | float32 | **dynamic 축 없음** |

- 축 의미: (배치 1, **노드 3**, **서브캐리어 64**, **시간 3000** = 30초 @ 100 Hz)
- 전처리 (`m2_runtime.preprocess_window` 가 수행, 그래프 바깥):
  1. 프레임별 피크 정규화 — 각 프레임을 그 프레임의 최댓값으로 나눔 (ESP 측과 동일)
  2. 가드 서브캐리어 `[0,1,2,3,4,5,32,59,60,61,62,63]` 을 0
- 런타임 `infer()` 는 수집기 자연 배치인 `(3, 3000, 64)` (노드×시간×서브캐리어)를 받아
  위 전처리 후 `(1,3,64,3000)` 로 전치한다.

> **배치 추론은 지원하지 않는다.** 창 단위 스트리밍 추정기다.
> 출력에 배치 축이 없으므로 입력도 1 로 고정했다. `batch=2` 를 넣으면 onnxruntime 이
> `InvalidArgument` 로 거부한다 (검증 [1b]). 그래프 안쪽의 고정 reshape 도 이중 방어로 남겨 뒀다.

> 가드 목록은 추측이 아니다. 수집 데이터 3노드 전부에서 이 12개 채널의 표준편차가 정확히 0 임을
> 확인했고, 802.11n HT20 이 64개 중 52개만 쓴다는 사실과도 맞는다.

> **`configs/m2_vital.yaml` 의 `window_frames: 1000` 과 다르다.** 그건 이번 제출에 포함하지 않은
> LSTM 학습 경로의 값이고, 거기엔 `FIXED — train == infer` 주석이 붙어 있다.
> 나중에 LSTM 경로를 되살린다면 두 창 길이를 맞춰야 한다.

### 출력 (모두 float32)

| 이름 | shape | 내용 |
|---|---|---|
| `resp_spectrum` | `(3, 151)` | 0~5.0 Hz, 1/30 Hz 간격, 가드 제외 52채널 평균 **크기** |
| `resp_bpm` | `(3,)` | 0.1~0.6 Hz 대역 ArgMax bin × 60 |
| `resp_snr_db` | `(3,)` | 대역 내 peak / median-background, dB |
| `heart_bpm` | `(3,)` | 0.8~3.0 Hz 대역 |
| `heart_snr_db` | `(3,)` | 〃 |

대역 → bin 구간. **네 경계 모두 정확히 정수 bin 에 떨어진다** (부동소수 비교 없이 정수로 박음):

| 대역 | bin | 개수 | bpm 범위 |
|---|---|---|---|
| 호흡 0.1–0.6 Hz | 3 … 18 | 16 | 6 … 36 |
| 심박 0.8–3.0 Hz | 24 … 90 | 67 | 48 … 180 |

### bpm 해상도는 2.0 회/분이다

창 3000프레임 → bin 간격 1/30 Hz = 2.0 bpm 이고, 지시에 따라 포물선 보간을 넣지 않았다
(ONNX Gather 회피). 따라서 출력은 **2.0 의 배수만** 나온다:

- `resp_bpm` ∈ {6, 8, 10, …, 36} (16개)
- `heart_bpm` ∈ {48, 50, 52, …, 180} (67개)

10초 창일 때의 6.0 회/분에서 **3배 개선**됐다 (호흡 대역 bin 6개 → 16개).

> **15.0 회/분(0.25 Hz)은 이 격자에서 나올 수 없다.** 15 는 2.0 의 배수가 아니고,
> 0.25 Hz 는 bin 7.5 로 정확히 두 bin 사이에 걸린다. 14.0 또는 16.0 만 가능하며
> 오차 1.0 (반 bin) 이 보간 없는 ArgMax 의 원리적 한계다. 검증 [3a] 참조.

## 4. 그래프 구성

`torch.fft` 를 쓰지 않는다. 전부 고정 가중치 연산이다.

1. **선형 추세 제거** — 설계행렬 `A(3000×2)` 와 유사역행렬 `B(2×3000)` 를 상수로 박고
   `x - A @ (B @ x)`. 3000×3000 투영행렬(36 MB)은 만들지 않는다.
2. **DFT** — bin 0..150 만 뽑는 cos/sin 기저 `(151×3000)` 2개를 frozen Linear weight로.
   `magnitude = sqrt(re² + im² + 1e-12)`
3. **채널 결합** — 가드 마스크를 곱하고 합산 후 52로 나눈다.
   (가드 채널은 이미 0이지만 크기 계산에 `sqrt(0+0+1e-12)=1e-6` 이 남아, 64로 나누면 편향이 생긴다)
4. **ArgMax** — 포물선 보간 없음. 동점이면 앞쪽 bin (ONNX 기본 동작).
5. **SNR** — ONNX에 Median 연산이 없어 `TopK(k=대역폭, 내림차순)` + **고정 Slice** 로 구했다.
   Gather를 쓰지 않았다.

생성된 그래프의 연산자: `MatMul×4, TopK×2, ArgMax×2, Slice×7, Reshape×5, Log×2, Sqrt×1,
ReduceSum×1, Add×9, Mul×8, Div×3, Sub×1, Cast×2, Squeeze×2, Constant×51`.
**Gather 없음.** 상수 파라미터 912,000개 (추세 6,000 + DFT 906,000) → 파일 3.68 MB.

### SNR 단위에 대한 결정 (검토 요망)

`resp_spectrum` 이 **크기(magnitude)** 로 정의돼 있으므로 SNR을 `20·log10(peak/median)` 로 계산했다.
같은 양의 파워비 dB와 수치가 같아져서 `configs/m2_vital.yaml` 의 `gate_db: 6.0` 눈금이 그대로 맞는다.

다만 `src/m2_vital/snr.py` 와 **완전히 같지는 않다.** 남은 차이는 채널 결합 순서 하나다:

| | snr.py | 이 ONNX |
|---|---|---|
| 채널 결합 | 64채널 **파워** 평균 | 52채널 **크기** 평균 |
| 피크 정밀화 | 포물선 보간 | ArgMax bin |
| 창 길이 | 3000 | 3000 ← **이번에 일치시킴** |

`mean(|X|)² ≠ mean(|X|²)` 이라 SNR 값이 완전히 같지는 않지만, 창 길이를 맞춘 결과
실측 차이는 **0.06 ~ 0.40 dB** 수준이다 (검증 [4c]).

### [3a] 합성 사인파 → 기저 행렬 검증 (그래프 직접 입력)

bin 간격 2.0 회/분 → 보간 없는 ArgMax 의 이론 최대 오차 = 반 bin **1.0**

| 입력 | bin 위치 | 기대 | 실제 | 오차 | 허용 | |
|---|---|---|---|---|---|---|
| 0.2000 Hz | 6.0 (중심) | 12.0 | `[12. 12. 12.]` | 0.0 | 0.0 | OK |
| 0.2333 Hz | 7.0 (중심) | 14.0 | `[14. 14. 14.]` | 0.0 | 0.0 | OK |
| 0.3000 Hz | 9.0 (중심) | 18.0 | `[18. 18. 18.]` | 0.0 | 0.0 | OK |
| 0.2500 Hz | **7.5 (비정수)** | 15.0 | `[14. 14. 14.]` | **1.0** | 1.0 | OK |

**bin 중심 주파수 세 개가 오차 0.0 으로 맞으므로 기저 행렬은 정확하다.**

> 0.25 Hz → 15.0 이 오차 0 으로 나올 것이라는 예상은 **성립하지 않는다.**
> 2.0 회/분 격자에서 가능한 값은 짝수뿐이고 15 는 홀수다. 0.25 Hz 는 bin 7.5 로
> 정확히 두 bin 사이에 걸려 14.0 또는 16.0 만 나올 수 있다. 오차 1.0 이 한계이며,
> 이는 10초 창일 때의 3.0 에서 개선된 값이다. 기저가 틀린 게 아니다.

### [3b] 같은 사인파를 전처리 경유로 입력 — 1-1(a)절의 근거

```
정규화 후 채널별 시간축 표준편차 최대 = 0.000e+00
resp_bpm = [6. 6. 6.]     ← 신호가 완전히 지워져 호흡 대역의 첫 bin(3 → 6.0)만 남음
```

### [3c] 차동 변조는 전처리를 통과하는가

0.30 Hz 차동 변조 → `[18. 18. 18.]`, 오차 **0.0** OK

### [4] `out/vital_spectrum.csv` 를 만든 실제 창

## 8. 남은 결정 사항

창 길이와 배치 축은 **확정됐다** (3절). 남은 것은 아래 둘이다.

1. **SNR 단위** — `20·log10(크기)` 로 갔고 `snr.py` 의 64채널 파워 평균과 채널 결합 순서가 다르다.
   실측 차이는 0.06~0.40 dB 로 작지만 정확히 같지는 않다 (4절, [4c]).
   두 경로의 SNR을 완전히 같은 수로 맞춰야 한다면 계약 변경이 필요하다.
2. **포물선 보간** — 현재 지시대로 넣지 않았다. bpm이 2.0 배수로만 나온다.
   소수점이 필요하면 런타임 쪽(`m2_runtime.py`)에서 `resp_spectrum` 을 받아
   후처리로 넣는 방법이 있다. ONNX 그래프는 건드리지 않아도 된다.

그리고 **10월 1순위는 1-1(e)의 진단**이다 — 정규화 전 프레임 피크값을 컬럼으로 추가해 1분 수집.

## 9. 미확인 / 범위 밖

- `snr.py` 의 `band_power_spectrum` 은 창 함수를 걸지 않는다(사각창). 낮은 주파수 누설이
  결과를 얼마나 바꾸는지 **측정하지 않았다.** 수정 금지 대상이라 그대로 뒀다.
- 이 ONNX를 rp5 실기에서 돌려보지 **않았다.** CPU EP + onnxruntime 1.30.0 (Windows) 에서만 확인했다.
- 1-1(b)의 "34세션 17,034프레임" 수치는 **M1 측 확인 결과이고 이 레포에서 재현하지 않았다.**
- `*_fall*`, `*_hardneg_*` 파일(약 800 MB)은 읽지 않았다. 부정 결과는 `*_normal_*` 16개 기준이다.
- 창을 3000으로 늘렸으므로 `out/vital_spectrum.csv` 를 다시 만들 필요는 없다
  (그건 이미 30초 창이다). 1절의 통과율 수치도 그대로 유효하다.
