# M1 회신 답변 및 통합 반영 — 2026-09-17

김태연님 회신 확인했습니다. 0 입력에서 `fall_score=0.595926`이 반복된 원인과 학습 로더의
격자 처리 차이에 대한 진단에 동의합니다. 아래 항목은 `C:\rp5` 로컬 통합 트리에 반영했고,
아직 RPi5에서 재측정하지 않았습니다.

## 반영한 통합 계약

| 회신 항목 | 로컬 반영 |
|---|---|
| 전역 200ms | `M1_INFER_INTERVAL_MS` 기본값을 200ms(5Hz)로 변경. 노드별 추론은 하지 않음 |
| 100Hz 격자 | M1 raw 버퍼를 삭제하지 않고 누락 프레임을 0으로 채움. ESP의 uint32 ms 시계 wrap을 처리하며, 소폭 역행 패킷은 늦은 패킷으로 버림 |
| 창끝 게이트 | 필수 학습 노드 `1,2,3`의 최근 실제 프레임이 현재 Redis 수신 시각 기준 10ms 이내일 때만 추론 |
| K=3/N=5 | 최근 5회의 창 판정 중 3회 이상일 때 `fall_detected=true`. 5회가 모이기 전에는 양성으로 확정하지 않음 |
| 입력 부족 | `input_status=insufficient_input`, `infer_source=skipped`, `insufficient_input=true`를 별도로 기록. 0.596을 sentinel로 사용하지 않음 |
| M5 연결 | K/N 집계가 성립한 M1 결과는 통합 위험도 0.65 floor를 통해 M5 평가로 연결. 단일 창 양성은 이 floor를 만들지 않음 |
| M2 | 미학습 스텁은 코드/API/대시보드 기본값을 off로 조정. 스텁 파일과 모델 계약은 삭제하지 않음 |

창끝 게이트가 실패한 tick은 같은 200ms 구간의 다음 패킷에서 다시 확인할 수 있게 타이머를
전진시키지 않았습니다. 따라서 tick 경계 직후 도착한 나머지 필수 노드를 기다릴 수 있습니다.

## 회신이 필요한 사항

1. K/N 집계는 위와 같이 **N=5개가 모인 뒤** 판정하도록 해석했습니다. 3개만 모인 초기
   구간에서도 3/3을 양성으로 인정해야 한다면 알려 주세요.
2. 창끝의 10ms 허용치는 RPi5 수신 시각 기준으로 두었습니다. ESP 노드별 `ts_ms`는 서로
   동기화되지 않으므로, zero-fill 간격은 각 노드의 uint32 장치 시계, 생존 게이트는 호스트
   수신 시각을 사용했습니다. 이 해석으로 게이트 통과율을 RPi5에서 확인하겠습니다.
3. 집계 전 raw `fall_score`는 M5 문맥에 보존했습니다. K/N 미달 raw score까지 M5의 위험도
   보정·키워드 결합에서 완전히 억제해야 한다면 downstream 계약을 맞추겠습니다. 현재는
   단일 창 양성이 M1 consensus floor를 만들지 않도록만 제한했습니다.

## CSI2 진단 포맷

`CSI2` 792B(`struct.Struct("<4sBBHIIhH193f")`) 제안은 진단용 1분 수집에 유용하므로
진행 찬성입니다. 다만 현재 저장소는 `CSI!` 788B 고정 계약을 사용하고 새 UDP/Redis 필드·키를
추가할 때 운영 확인이 필요합니다. 아래 조건을 확인받은 뒤 펌웨어 커밋과 함께 한 번에 반영하겠습니다.

- 기존 `CSI!` 788B 파서는 계속 수용하고 `CSI2`만 magic으로 분기
- `frame_peak`는 진단 필드로만 보존하며 M1/M5 판단에는 사용하지 않음
- 792B 실측 수집 기간과 종료 시점을 명시하고, 장기 기본 포맷으로 승격하지 않음
- 펌웨어 커밋·샘플 캡처·필드 의미를 공유한 뒤 sensing 파서와 테스트를 같이 변경

## 성능 수치 인용 범위

기존 RPi5 결과의 M1은 실창이 아닌 0 입력 결과였으므로 M1 정확도·운영 감지율로 인용하지
않겠습니다. K=3 결과 `11/19`와 빈 방 118.4초 관찰은 모델 담당자 검증 자료로 기록하되,
FA/h와 시스템 성능으로 확정하지 않습니다. 이번 로컬 변경은 코드·단위 테스트만 통과한
상태이며, 다음 모델 업데이트 후 스왑을 비운 동일 조건의 RPi5 단일 재측정이 필요합니다.
